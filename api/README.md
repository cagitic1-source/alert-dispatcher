# alert-dispatcher

Сервис приёма и асинхронной доставки алертов. gRPC API принимает алерты, Redis хранит их состояние, воркер доставляет с ретраями и отправляет неудачные в dead-letter queue.

```
Клиент --CreateAlert(idempotency_key)--> API
                                          |
                            [Lua: резервация + Hash + XADD]
                                          |
                                 Stream alerts:pending
                                          |
                              Worker (consumer group)
                                          |
                     доставка -> delivered | retry -> DLQ
```

## Гарантии

- **Доставка — at-least-once.** Сообщение подтверждается (XACK) только после завершения обработки. Если воркер упадёт посередине, сообщение останется в PEL и будет перезабрано. Exactly-once не достигается: подтверждение обработки и сам факт доставки — две разные операции, между которыми процесс может умереть. Поэтому каждый шаг обработки идемпотентен, а принимающая сторона (когда появится реальная доставка) должна быть готова к повторам.
- **Создание алерта идемпотентно** в пределах часа — окно задаётся `idemTTL`. Повторный `CreateAlert` с тем же ключом вернёт существующий алерт, а не создаст второй. Резервация ключа, запись состояния и постановка в очередь выполняются одним Lua-скриптом, то есть атомарно.
- **Отправка в DLQ однократна** в пределах `markerTTL` (сутки). Маркер и запись в `alerts:dead` пишутся одним Lua-скриптом, поэтому состояния «маркер есть, записи нет» не существует.
- **Падение воркера не теряет алерт.** Неподтверждённое сообщение остаётся в PEL и через `claimMinIdle` (2 минуты) подбирается `XAUTOCLAIM` — ценой возможного повтора обработки.
- **Повторы доставки идут с экспоненциальной задержкой.** При неудаче счётчик попыток увеличивается, повтор планируется в sorted set `alerts:retry` на `baseRetryDelay * 2^(attempts-1)` (30с → 60с → 120с). После `maxAttempts` (3) алерт уходит в `alerts:dead` и получает статус `failed`.
- **Хранение ограничено по времени и по надёжности.** Алерт живёт сутки (`alertTTL`), затем удаляется по TTL — сервис не хранит историю и не является источником истины для аудита. Redis запущен с AOF (`appendonly yes`), но при `appendfsync everysec` возможна потеря до секунды записей; постоянные тома в текущем compose-файле не настроены.

## Известные ограничения

- **Таймаут доставки обязан быть меньше `claimMinIdle`.** Если доставка зависнет дольше порога, claimStale другого воркера перехватит сообщение, которое ещё обрабатывается, и алерт доставится дважды. Соотношение закреплено в коде: вызов `deliver` обёрнут в `context.WithTimeout(ctx, deliverTimeout)`, а тест `TestDeliverTimeoutShorterThanClaimMinIdle` падает при нарушении.
- **Гонка на очереди повторов.** Два воркера могут одновременно получить один и тот же ID из `DueRetries` и оба вернуть его в `alerts:pending` — алерт попадёт в поток дважды. При at-least-once это допустимо. Закрывается Lua-скриптом, который делает `ZRANGEBYSCORE` + `ZREM` + `XADD` атомарно; сейчас не сделано, потому что воркер запускается в одном экземпляре.
- **XTRIM не смотрит в PEL.** Обрезка режет по MINID, то есть по возрасту сообщения, и ничего не знает о том, подтверждено оно или нет. Если воркер простоит дольше `trimMaxAge` (сутки), неподтверждённые сообщения будут срезаны вместе со старыми. Защита — только запас порога относительно реального времени обработки.
- **Окно идемпотентности конечно.** Маркер DLQ живёт `markerTTL` (сутки), ключ идемпотентности создания — час. После истечения повтор той же операции пройдёт как новый. Окна подобраны с запасом относительно времени жизни сообщения в системе (минуты), но не дают защиты навсегда.
- **Lua-скрипты не покрыты юнит-тестами.** Содержимое `create_idempotent.lua` и `dlq_send_once.lua` выполняется на стороне Redis, поэтому фейки его не видят: юнит-тест проверяет, что метод был вызван с правильными аргументами, но не то, в какой стрим ушла запись. Это покрывается только интеграционными тестами с реальным Redis.
- **DLQ надо вычитывать наружу.** `alerts:dead` накапливает записи, но потребителя у него нет — разбор неудачных алертов сейчас ручной.

## Компромиссы

- **Redis Streams, а не Kafka.** Redis уже в стеке под состояние алертов, а объёмы не требуют отдельного брокера. Streams дают consumer group, явное подтверждение и `XAUTOCLAIM` для подбора зависших — этого достаточно для at-least-once. Kafka имела бы смысл при долгом хранении, перечитывании потока с начала или объёмах, не влезающих в память; ценой отдельной инфраструктуры.
- **Redis Streams, а не Pub/Sub и не List.** Pub/Sub теряет сообщения: нет подписчика в момент публикации — сообщение исчезло. List через `BRPOP` не умеет подтверждать обработку: сообщение уходит из очереди в момент чтения, и падение воркера теряет его безвозвратно.
- **Hash, а не JSON-строка.** Состояние алерта меняется по частям: `HSET alert:id status delivered` трогает одно поле. С JSON пришлось бы читать весь объект, править и писать обратно — два сетевых похода и гонка между ними.
- **Lua, а не MULTI/EXEC.** MULTI/EXEC даёт атомарность, но не даёт условной логики: внутри транзакции нельзя посмотреть на результат предыдущей команды и решить, выполнять ли следующую. Идемпотентное создание и однократная отправка в DLQ требуют именно ветвления, поэтому оба сделаны скриптами.
- **Состояние в Redis, история — наружу.** Очередь, PEL, маркеры идемпотентности и очередь повторов — рабочее состояние, оно живёт столько же, сколько обработка, и ему место в Redis. История доставок для отчётов и аудита нужна после и требует запросов с фильтрами — это задача для Postgres, а не для лога. Сейчас история не пишется никуда, это осознанная граница учебного проекта.
